## 1. 목적

본 문서는 한살림 부산 PMS 프로젝트에서 Worker가 일관된 방식으로 작업하고, 구현·검증·보고·인계 과정에서 누락이 발생하지 않도록 운영 기준을 정리한다.

Worker는 승인된 설계와 TASK를 기준으로 작업하며, 실제 반영과 실행 검증을 완료한 결과만 제출한다.

## 2. 적용 범위

| 적용 대상 | 적용 내용 |
|---|---|
| 기능 구현 | 승인된 TASK와 설계에 따른 코드 작성 및 수정 |
| Apps Script | 프로젝트 파일 반영, 저장 확인, 실제 함수 실행 |
| Google Sheets | 시트·컬럼·설정 반영 및 결과 확인 |
| 테스트 | 정상·오류·회귀 테스트 수행 및 결과 기록 |
| 문서 | 구현 보고, 테스트 결과, CHANGELOG, Release 기록 |
| 인계 | 현재 상태, 완료 항목, 미완료 항목, 다음 조치 전달 |
| Review | PASS 또는 REVISE 판정에 따른 후속 조치 |

## 3. Worker 역할

| 역할 | 책임 |
|---|---|
| 구현 | 승인된 요구사항과 설계에 따라 기능을 구현한다. |
| 반영 | Apps Script와 Google Sheets에 변경사항을 반영한다. |
| 실행 | 실제 Apps Script 환경에서 대상 기능을 실행한다. |
| 검증 | 기능 테스트와 기존 기능 회귀 테스트를 수행한다. |
| 오류 수정 | 발견된 오류의 원인을 분석하고 작업 범위 안에서 수정한다. |
| 재테스트 | 수정한 항목과 영향받는 기존 기능을 다시 검증한다. |
| 보고 | 추가·수정 파일, 구현 내용, 테스트 결과와 Release 정보를 제출한다. |
| 인계 | 다른 AI 또는 Worker가 작업을 이어갈 수 있도록 HANDOVER 정보를 작성한다. |

## 4. 작업 원칙

| 번호 | 원칙 | 적용 기준 |
|---:|---|---|
| 4.1 | 승인된 TASK 기준 | 사용자와 Technical Lead가 승인한 범위만 수행한다. |
| 4.2 | 기존 구조 유지 | 승인된 Architecture, API, 파일 구조와 업무 흐름을 유지한다. |
| 4.3 | 실제 반영 | 코드 작성만으로 완료하지 않고 대상 환경에 반영한다. |
| 4.4 | 실제 실행 | Apps Script에서 기능을 실행하고 결과를 확인한다. |
| 4.5 | 테스트 후 보고 | 오류 수정과 재테스트까지 완료한 후 구현 결과를 보고한다. |
| 4.6 | 변경 추적 | 주요 변경은 CHANGELOG와 Release 정보에 기록한다. |
| 4.7 | 승인 후 진행 | Architecture Review의 PASS 판정과 다음 TASK 승인 후 후속 작업을 진행한다. |
| 4.8 | 공식 저장소 기준 | 최종 산출물은 `F:\HLAS\`의 해당 폴더를 기준으로 관리한다. |

## 5. 작업 금지 사항

| 번호 | 금지 사항 |
|---:|---|
| 5.1 | 승인받지 않은 다음 TASK를 임의로 진행하지 않는다. |
| 5.2 | 정적 코드 검토만으로 실제 실행 테스트가 완료되었다고 보고하지 않는다. |
| 5.3 | 실행하지 않은 기능을 PASS로 기록하지 않는다. |
| 5.4 | 승인된 Architecture, API 또는 기존 기능을 작업 범위 밖에서 변경하지 않는다. |
| 5.5 | 오류, 미반영 항목 또는 미완료 테스트를 숨기거나 생략하지 않는다. |
| 5.6 | CHANGELOG와 Release 기록이 필요한 변경을 기록 없이 완료 처리하지 않는다. |
| 5.7 | 임시 작업 공간을 프로젝트의 공식 저장소로 사용하지 않는다. |

## 6. 제출 형식

Worker의 구현 완료 보고는 다음 순서를 유지한다.

| 번호 | 제출 항목 | 필수 내용 |
|---:|---|---|
| 1 | 추가 파일 | 파일명, 생성 목적, 주요 기능 |
| 2 | 수정 파일 | 파일명, 수정 이유, 변경 내용 |
| 3 | 구현 기능 | 구현한 기능 목록 |
| 4 | Apps Script 반영 | 반영 여부, 변경 사항, 저장·실행 순서 |
| 5 | 실행 테스트 | 테스트 항목별 PASS/FAIL |
| 6 | 오류 수정 | 오류, 원인, 수정 내용 |
| 7 | 재테스트 | 수정 후 최종 PASS 여부 |
| 8 | 공통모듈 후보 | 중복 코드와 리팩터링 대상 |
| 9 | Release | 버전, 변경 이력, 공식 산출물 |

보고 마지막에는 다음 형식을 사용한다.

```text
TASK-XXXX 완료

Architecture Review를 요청합니다.

PASS 판정이 나오면 다음 TASK 진행 여부를 알려주세요.
```

## 7. AI 교체 절차

| 단계 | 수행 내용 |
|---:|---|
| 1 | 현재 Worker는 HANDOVER 문서를 작성한다. |
| 2 | 진행 중인 TASK, 완료 범위, 미완료 범위와 오류를 명시한다. |
| 3 | 변경 파일과 공식 저장 위치를 기록한다. |
| 4 | 실행한 테스트와 실행하지 못한 테스트를 구분한다. |
| 5 | 교체된 AI는 공식 문서와 HANDOVER를 먼저 확인한다. |
| 6 | 교체된 AI는 현재 상태를 확인한 뒤 승인된 TASK 범위에서 작업을 재개한다. |
| 7 | 이전 Worker가 완료하지 않은 작업을 검증 없이 완료로 간주하지 않는다. |

## 8. HANDOVER 절차

HANDOVER에는 다음 정보를 포함한다.

| 항목 | 기록 내용 |
|---|---|
| 프로젝트 | 프로젝트명과 공식 저장소 |
| TASK | Task ID, 버전, 목적, 승인된 범위 |
| 현재 상태 | 완료, 진행 중, 대기, 차단 상태 |
| 변경 파일 | 추가·수정 파일과 저장 경로 |
| 반영 상태 | Apps Script·Google Sheets 반영 여부 |
| 테스트 | 실행 항목, PASS/FAIL, 실행 로그 |
| 오류 | 오류 내용, 원인, 수정 여부 |
| 미완료 | 남은 작업과 필요한 사용자 조치 |
| 다음 조치 | 재실행, 재테스트 또는 Review 요청 |

HANDOVER 이후 작업자는 전달받은 내용과 실제 파일·실행 환경을 대조하여 상태를 확인한다.

## 9. Review 대응 절차

| Review 결과 | Worker 조치 |
|---|---|
| PASS | 결과를 확인하고 다음 TASK 승인 여부를 기다린다. |
| REVISE | Review 의견을 작업 범위에 반영하고 실제 환경에서 재테스트한다. |
| 추가 확인 요청 | 요청된 로그, 파일, 실행 결과를 확인하여 보완 보고한다. |
| 환경 문제 | 원인을 기록하고 환경 정상화 후 동일 테스트를 다시 실행한다. |

REVISE 대응 시에는 수정 파일, 수정 이유, 오류 원인, 재테스트 결과를 다시 제출하고 Architecture Review를 재요청한다.
